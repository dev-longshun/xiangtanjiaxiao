**文档版本**：v1.0  
**创建日期**：2025年12月5日  
**功能模块**：用户认证与登出管理

## 一、设计概述

### 问题分析

传统 JWT 认证有个问题：**Token 一旦签发，在有效期内始终有效，无法主动失效**。

例如：
- 用户 Token：`eyJhbGci...`，24小时有效
- 即使用户调用"退出登录"，老 Token 仍然可以使用
- 如果 Token 被泄露，别人可以继续使用（直到24小时后自动过期）

### 解决方案：Token 黑名单机制

**核心思路**：
1. 用户退出登录时，将 Token 加入**黑名单**
2. 之后每次请求都检查 Token 是否在黑名单中
3. 黑名单中的 Token 被拒绝（即使尚未过期）
4. 定期清理已过期的 Token（节省内存）

## 二、架构设计

### 2.1 系统流程图

```

│  用户发起请求 (携带 Authorization: Bearer {token})           │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
        ┌──────────────────────────────┐
        │  JwtAuthenticationFilter      │
        │  (JWT 认证过滤器)            │
        └──────────────┬───────────────┘
                       ↓
        ┌──────────────────────────────┐
        │  1. 提取 Token               │
        │  2. 验证签名和有效期          │
        └──────────────┬───────────────┘
                       ↓
        ┌──────────────────────────────┐
        │  检查黑名单                  │
        │  isBlacklisted(token)?       │
        └──────┬──────────────────────┘
              / \
            NO   YES
            /     \
          ✓       ✗ (拒绝请求 - 返回 401)
          │
          ↓
        ┌──────────────────────────────┐
        │  解析用户信息                │
        │  - username                  │
        │  - roles                     │

          │
          ↓
        ┌──────────────────────────────┐

        │  继续处理请求               │
        └──────────────────────────────┘
```

- 定期清理过期的 Token

**关键方法**：
```java

    // 将 Token 加入黑名单，expiryTime 为 Token 过期时间

public boolean isBlacklisted(String token)
    // 检查 Token 是否在黑名单中

private void cleanupExpiredTokens()
    // 后台线程：每5分钟清理一次过期 Token
```

#### JwtAuthenticationFilter（JWT 认证过滤器）

**职责**：
- 拦截所有请求
- 检查黑名单（新增）

- 提取用户信息并放入 SecurityContext

**流程变化**：
```
原：Token 验证 → 解析用户 → 设置 Security

                    ↑ (新增步骤)
```

**新增方法**：

## 三、退出登录流程

### 3.1 用户端流程

```
前端页面
    ↓
用户点击"退出登录"按钮
    ↓
前端发送请求到后端
POST /api/auth/logout
Header: Authorization: Bearer {token}
    ↓
后端验证 Token 并加入黑名单
    ↓
前端收到响应（code=200）
    ↓
前端执行：
1. 删除 localStorage 中的 Token
2. 删除 localStorage 中的 username
3. 清空用户信息
4. 跳转到登录页面
```

### 3.2 后端处理流程

```
AuthController.logout()
    ↓
1. 从 HTTP 请求头提取 Token
   Authorization: Bearer xxx
    ↓
2. 调用 jwtUtil.validateToken(token)
   - 检查签名是否有效
   - 检查 Token 是否过期
   - 如果无效 → 返回 401 错误
    ↓
3. 调用 jwtUtil.getExpiryTimeFromToken(token)
   - 从 Token 的 Payload 中提取过期时间
   - 例如：1733414400000（毫秒戳）
    ↓
4. 调用 blacklistManager.addToBlacklist(token, expiryTime)
   - 将 Token 存入黑名单
   - 设置过期时间为 Token 原有效期
    ↓
5. 返回成功响应
   {
     "code": 200,
     "data": null,
     "message": "退出登录成功"
   }
```

## 四、接口规范

### 4.1 退出登录接口

**请求**：
```http
POST /api/auth/logout
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

**响应成功（200 OK）**：
```json
{
  "code": 200,
  "data": null,
  "message": "退出登录成功"
}
```

**响应错误 - Token 无效**（401 Unauthorized）：
```json
{
  "code": 401,
  "data": null,
  "message": "Token 无效或已过期"
}
```

**响应错误 - 未找到 Token**（401 Unauthorized）：
```json
{
  "code": 401,
  "data": null,
  "message": "未找到有效的 Token"
}
```

### 4.2 前端集成示例

```javascript
// 1. 获取 Token
const token = localStorage.getItem('token');

// 2. 发送退出登录请求
fetch('http://localhost:7070/api/auth/logout', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer ' + token
  }
})
.then(res => res.json())
.then(result => {
  if (result.code === 200) {
    // 3. 清除本地数据
    localStorage.removeItem('token');
    localStorage.removeItem('username');
    localStorage.removeItem('nickname');
    
    // 4. 提示用户
    alert('已退出登录');
    
    // 5. 跳转到登录页
    window.location.href = '/login';
  } else {
    alert('退出登录失败: ' + result.message);
  }
})
.catch(err => {
  console.error('退出登录出错:', err);
  // 即使失败，也应该清除本地 Token
  localStorage.removeItem('token');
  window.location.href = '/login';
});
```

## 五、黑名单清理机制

### 5.1 为什么需要清理？

**内存占用问题**：
- 如果有 1 万用户，每天产生 1 万个 Token
- 黑名单会无限增长，最终耗尽内存
- 解决方案：定期删除已过期的 Token

### 5.2 清理策略

**清理时机**：后台线程，每5分钟执行一次

**清理逻辑**：
```
遍历黑名单中的所有 Token
  if (Token的过期时间 <= 当前时间) {
    从黑名单中删除此 Token
  }
```

**示例**：
```
当前时间：2025-12-05 14:30:00

黑名单中的 Token：
  Token1: 过期时间 2025-12-05 12:00:00 ✗ 已过期，删除
  Token2: 过期时间 2025-12-05 14:00:00 ✗ 已过期，删除
  Token3: 过期时间 2025-12-05 16:00:00 ✓ 未过期，保留
  Token4: 过期时间 2025-12-05 18:30:00 ✓ 未过期，保留

结果：清理前 4 个 Token，清理后 2 个 Token
```

### 5.3 监控和告警

可以通过以下方式监控黑名单大小：

```java
// 获取当前黑名单大小
int size = blacklistManager.getBlacklistSize();
log.info("当前黑名单大小: {} 个 Token", size);

// 如果黑名单大小超过阈值，记录告警
if (size > 10000) {
  log.warn("黑名单过大，已有 {} 个 Token，请检查", size);
}
```

## 六、安全考虑

### 6.1 Token 泄露情况

**场景1**：用户设备被盗
- 用户发现后立即登录，然后退出
- 旧 Token 被加入黑名单，无法继续使用

**场景2**：Token 在网络传输中被截获
- 攻击者获得了 Token
- 如果用户不知道，Token 仍然有效
- 需要依赖 HTTPS 加密传输

**场景3**：用户主动退出登录**
- 用户点击"退出登录"按钮
- 前后端配合将 Token 加入黑名单
- 旧 Token 立即失效

### 6.2 黑名单本身的安全

| 风险 | 缓解措施 |
|------|--------|
| 黑名单在内存中，服务器重启丢失 | 在单机部署中可接受；生产环境建议用 Redis |
| 攻击者试图篡改黑名单 | 只有后端可访问，前端无法直接操作 |
| 黑名单过大导致性能问题 | 自动清理过期 Token，监控大小 |

### 6.3 最佳实践

1. **前端要求**：
   - 退出登录后立即清除本地 Token
   - 如果后端返回 401，也要清除本地 Token
   - 定期检查 Token 有效性（如刷新页面时）

2. **后端要求**：
   - 每次请求都检查黑名单
   - 定期清理过期 Token
   - 监控黑名单大小和性能

3. **部署要求**：
   - 使用 HTTPS 加密传输
   - 设置较短的 Token 有效期（如4小时）
   - 在生产环境使用 Redis 而非内存存储

## 七、分布式部署方案

### 7.1 当前方案的局限

**当前**：使用内存 ConcurrentHashMap 存储黑名单
- ✓ 简单，适合单机
- ✗ 多机部署时，每个实例有独立的黑名单

**问题场景**：
```
用户在实例A退出登录
  ↓
Token 被加入实例A的黑名单
  ↓
用户在实例B发起请求
  ↓
实例B的黑名单中没有此 Token
  ↓
请求被接受（本应被拒绝！）
```

### 7.2 改进方案：使用 Redis

如果需要分布式部署，将黑名单存到 Redis：

```java
@Component
public class RedisTokenBlacklistManager {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    private static final String BLACKLIST_PREFIX = "token:blacklist:";
    
    /**
     * 将 Token 加入黑名单（存储到 Redis）
     */
    public void addToBlacklist(String token, long expiryTime) {
        long ttl = expiryTime - System.currentTimeMillis();
        
        if (ttl > 0) {
            // 使用 Token 过期时间作为 Redis key 的 TTL
            redisTemplate.opsForValue().set(
                BLACKLIST_PREFIX + token,
                "blacklisted",
                ttl,
                TimeUnit.MILLISECONDS
            );
        }
    }
    
    /**
     * 检查 Token 是否在黑名单中
     */
    public boolean isBlacklisted(String token) {
        return redisTemplate.hasKey(BLACKLIST_PREFIX + token);
    }
}
```

**优点**：
- ✓ 所有实例共享同一个黑名单
- ✓ Redis 自动清理过期 key（TTL）
- ✓ 支持分布式部署

## 九、常见问题（FAQ）

### Q1：为什么不使用数据库存储黑名单？

**A**：数据库不适合存储黑名单：
- 性能低：每次查询都需要数据库 I/O
- 管理复杂：需要手动清理过期数据
- 扩展性差：如果有大量并发请求，数据库可能成为瓶颈

**更好的选择**：
- 内存：适合单机，性能最好
- Redis：适合分布式，兼顾性能和可用性

### Q2：如果我忘记前端清除 Token 会怎样？

**A**：虽然 Token 已在后端黑名单中，但：
- 前端本地仍保存有 Token
- 如果网络中断，前端使用本地 Token 调用接口会失败（因为没网）
- 恢复网络后，黑名单会拒绝此 Token
- **建议**：前端必须清除本地 Token

### Q3：Token 有效期应该设多长？

**A**：需要在安全性和用户体验之间平衡：
- **短期**（4小时）：更安全，但用户体验差（需频繁重新登录）
- **中期**（12小时）：平衡方案，推荐
- **长期**（24小时）：用户体验好，但安全性较低

**当前设置**：24小时（可根据业务调整）

### Q4：黑名单清理会不会很频繁？

**A**：不会，因为：
- 清理线程每5分钟执行一次（后台线程，不阻塞主线程）
- 每次清理时间复杂度为 O(n)，其中 n = 当前黑名单大小
- 由于只有过期的 Token 才会被删除，n 的增长速度很慢

**性能影响**：几乎可以忽略不计

### Q5：如果服务器重启，黑名单会丢失吗？

**A**：是的，内存中的黑名单会丢失。

**影响分析**：
- 已退出的 Token 会重新变得有效（直到原有效期）
- 安全风险可接受（取决于你的安全需求）

**如果要求持久化**：
- 改用 Redis（自动持久化）
- 改用数据库（性能较低）

## 十、总结

### 核心要点

1. **无状态 vs 有状态**：
   - JWT 是无状态的，但通过黑名单机制获得"半有状态"的特性
   - 结合了两种方案的优点

2. **黑名单优势**：
   - ✓ 支持立即退出登录
   - ✓ 增强安全性（Token 泄露时可及时失效）
   - ✓ 内存占用可控（定期清理）

3. **前后端协作**：
   - 前端：调用退出接口 + 清除本地 Token
   - 后端：将 Token 加入黑名单

4. **生产部署**：
   - 单机：内存黑名单
   - 分布式：Redis 黑名单
