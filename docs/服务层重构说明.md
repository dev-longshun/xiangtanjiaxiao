# 服务层重构说明

## 概述

为提升代码的可测试性、可维护性和架构清晰度，本次重构将 `service` 包中的所有服务类拆分为 **接口** 和 **实现类** 两部分：

- **接口**：定义业务能力的契约，位于 `com.xiangtan.jiaxiao.service` 包下
- **实现类**：具体业务逻辑，位于 `com.xiangtan.jiaxiao.service.impl` 子包下

## 重构范围

本次重构涉及以下四个核心服务：

| 接口 | 实现类 | 职责描述 |
|------|--------|----------|
| `UserService` | `UserServiceImpl` | 用户管理（管理员登录、微信登录、用户查询与创建） |
| `SchoolService` | `SchoolServiceImpl` | 驾校信息管理（CRUD、搜索） |
| `ReviewService` | `ReviewServiceImpl` | 评价管理（提交、审核、查询） |
| `WeChatService` | `WeChatServiceImpl` | 微信网页授权登录（换取用户信息） |

## 目录结构

```

    └── WeChatServiceImpl.java # 微信服务实现
```

## 接口设计原则

1. **单一职责**：每个接口聚焦一个业务领域
2. **方法签名清晰**：使用简洁的中文注释说明方法用途
3. **返回类型明确**：避免使用 Object 等泛型返回类型
4. **无实现逻辑**：接口只定义契约，不包含具体实现

## 实现类规范

1. **命名规则**：接口名 + `Impl` 后缀
2. **注解使用**：
   - `@Service`：标记为 Spring 服务组件
   - `@RequiredArgsConstructor`（Lombok）：自动生成依赖注入构造器
3. **依赖注入**：使用 `final` 字段 + 构造器注入（推荐方式）
4. **方法实现**：必须添加 `@Override` 注解

## 依赖注入示例

### 控制器中使用服务接口

```java
@RestController
@RequestMapping("/api/schools")
@RequiredArgsConstructor
public class SchoolController {

    // 注入接口类型，Spring 会自动找到 SchoolServiceImpl 实现
    private final SchoolService schoolService;

    @GetMapping
    public List<School> getAllSchools() {
        return schoolService.getAllSchools();
    }
}
```

### Bootstrap 初始化器中使用

```java
@Component
@RequiredArgsConstructor
public class AdminInitializer implements CommandLineRunner {

    // 注入接口类型
    private final UserService userService;

    @Override
    public void run(String... args) {
        User admin = userService.getUserByUsername("admin");
        // ...
    }
}
```

## 优势与收益

### 1. 可测试性提升
- 可以使用 Mockito 等工具轻松 mock 接口，编写单元测试
- 无需依赖真实数据库或外部服务

```java
@Test
void testGetAllSchools() {
    SchoolService mockService = mock(SchoolService.class);
    when(mockService.getAllSchools()).thenReturn(testData);
    // 测试控制器逻辑...
}
```

### 2. 解耦与扩展性
- 控制器只依赖接口，不关心具体实现
- 可以轻松替换实现（如缓存实现、Mock 实现等）

### 3. 代码清晰度
- 接口文件简洁，快速了解业务能力
- 实现类专注业务逻辑，职责明确

### 4. 符合 SOLID 原则
- **依赖倒置原则（DIP）**：高层模块依赖抽象（接口），不依赖具体实现
- **开闭原则（OCP）**：对扩展开放，对修改封闭

## 注意事项

1. **无需修改已有代码**：控制器和 Bootstrap 类原本就注入的是接口类型（变量类型为 `UserService` 等），Spring 会自动找到唯一实现类并注入。
2. **避免循环依赖**：实现类之间尽量避免相互注入，推荐通过事件或消息机制解耦。
3. **接口粒度适中**：不宜过细（导致接口爆炸），也不宜过粗（违反单一职责）。

## 后续扩展建议

1. **DTO 提取**：对于 `WeChatService.WeChatUserInfo` 等内部类，可考虑移至独立的 `dto` 包。
2. **异常处理统一化**：在 Service 层统一抛出业务异常（如 `BusinessException`），由全局异常处理器统一处理。
3. **日志增强**：在关键业务逻辑（如登录、审核）添加详细日志，便于问题排查。
4. **单元测试覆盖**：为每个 Service 实现类编写单元测试，确保核心逻辑正确性。

## 重构影响范围

| 影响模块 | 是否需要改动 | 说明 |
|----------|--------------|------|
| Controller（控制器） | ❌ 否 | 已注入接口类型，无需修改 |
| Bootstrap（初始化器） | ❌ 否 | 已注入接口类型，无需修改 |
| Mapper（数据访问层） | ❌ 否 | 仅被 Service 实现类调用 |
| Config（配置类） | ❌ 否 | 不涉及 Service 依赖 |

## 验证方式

1. **编译检查**：执行 `mvn clean compile`，确保无编译错误
2. **单元测试**：运行 `mvn test`（如有测试用例）
3. **启动验证**：启动应用，访问 Swagger UI 或调用 API，验证功能正常
